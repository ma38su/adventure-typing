# 36ステージ一本道化：問題難度監査と再配置設計

## 結論

旧「1〜6年生 × 各6ステージ」は、物語の順番だけを引き継いだ36ステージの一本道にする。問題の難しさは漢字の量では決めず、実際に打つローマ字の長さ、文節数、ローマ字綴り、促音・拗音などの入力要素で決める。

現行は182問で、旧試算の各5コース×3問・計540問に対しても単純に358問不足する。この540問はUI初期検証時の下限であり、連続3D世界の全36標準ではない。また、旧学年の先頭で短文へ戻り、同じ学年内では急に長くなるため、現行順には中央値が8点以上変わる境界が28か所ある。データを旧順のまま連結してはいけない。

## 難度の測り方

監査値はゲーム内スコアではなく、問題配置を比較するための内部指標である。

- 主軸：空白を除いた実入力キー数
- 補助：文節数、モーラ数
- 加点：`shi`、`chi`、`tsu`、拗音系などの候補複雑さ、促音、拗音、撥音、長音
- 後半加点：数字、句読点、括弧などの記号
- 対象外：漢字の数、漢字の学年配当

同じ読みとローマ字なら、「海へ行く」と「うみへいく」は同じ難度になる。漢字にはルビを付け、読む難しさとタイピング難度を分離する。

監査は次のコマンドで再現できる。

```sh
node --test scripts/question-difficulty.node-test.mjs
node scripts/audit-question-difficulty.mjs
node scripts/audit-question-difficulty.mjs --json
```

## 入力要素の段階導入

| ステージ | 新しく扱う要素 | 運用 |
| ---: | --- | --- |
| 1–4 | 短い清音中心 | 1〜2文節。成功回数を優先 |
| 5–7 | 撥音 | 既習パターン内で少量 |
| 8–9 | 促音 | 1問に原則1か所 |
| 10–24 | 拗音、複雑なローマ字候補 | 長さと新要素を同時に跳ね上げない |
| 25–26 | `、` `。` `！` `？` | まず文末1記号、次に読点＋文末 |
| 27–28 | 長音 `ー` | 「コース」「チーム」など自然な語で導入 |
| 29–31 | 数字 | 1桁→2桁→時刻や個数。数字と記号の同時初出を避ける |
| 32–34 | かぎ括弧、括弧、中点 | 1問1種類から始める |
| 35–36 | 複合 | 既習要素を組み合わせるが、最大長は急増させない |

句読点などを表示だけにするか、実際に入力させるかは `romaji` が正本になる。入力対象なら `romaji` にも同じASCII文字を入れ、JIS/US配列差がある記号についてはキーボード設定と入力仕様を先に確定する。

## 物語に沿った再利用手順

1. 旧 `grade-stage` を新 `storyStage` 1〜36へ順番に対応させる。
2. 各既存問題へ監査値と旧話IDを付ける。
3. まず同じ話で目標帯に入る問題を残す。
4. 帯外問題は、意味が自然なら別の話へ候補として移す。旧IDは学習履歴リセット許容のため維持必須ではない。
5. 不足分を、その話の `intro`、`objective`、`completion` に沿った短文として追加する。
6. 各courseの難度中央値が原則として前course以下にならないこと、隣接ステージの中央値差が3点以内であることを機械検証する。
7. 新要素の初出ステージでは、新要素を含まない復習2問の後に導入1問を置く。

## 推奨学年は制限ではなく抽選ウェイトにする

各問題に `recommendedGrade` を持たせる。既存問題は旧学年を初期値として移行するが、一本道の解放条件や難度値には使わない。course開始時に、そのStage・courseで算定した必要数を難度帯内から選び、ユーザーの学年と `recommendedGrade` が一致する問題へ高いウェイトを与える。選んだ後は問題セットと順番を固定し、途中再開やリトライで問題が入れ替わらないようにする。

現行182問だけで各ステージ帯の候補を機械集計した結果は次の通り。これは物語との意味対応をまだ除外した上限値である。

| 推奨学年 | 15問以上の同学年候補があるステージ数 / 36 | 各ステージで15問に足りない延べ数※ | 1ステージ帯の同学年候補 最小–最大 |
| ---: | ---: | ---: | ---: |
| 1 | 3 | 221 | 0–16 |
| 2 | 0 | 316 | 2–9 |
| 3 | 0 | 335 | 0–10 |
| 4 | 0 | 363 | 0–12 |
| 5 | 0 | 394 | 0–9 |
| 6 | 0 | 425 | 0–6 |

※難度帯は隣接ステージ間で重なるため、新規問題数ではない。同学年だけで15問を組もうとした場合の、36ステージ分の不足診断である。実際は高ウェイト抽選なので、同学年候補が足りないときは他学年候補へ自然にフォールバックできる。ただし現状のままではほぼ全ステージでフォールバックが常態化するため、新規問題は各学年の語彙・関心に合わせて偏りなく作る。

旧 `grade` と実測難度帯が2段階以上離れる既存問題は82問ある。代表例は、推奨1年で実測4〜5相当の長文、推奨6年で実測2〜3相当の短い導入文である。これは誤データではない。`recommendedGrade` は文章内容の適性、実測難度は入力負荷という別軸なので、移行時に旧学年を機械的に変更しない。監査レポートの `gradeDifficultyMismatches` を、人手確認が必要な一覧として使う。

推奨する選出順は次の通り。

1. `storyStage` と難度帯で候補を絞る。
2. 同じ問題の直近出題、未解放要素、物語上不自然な問題を除外する。
3. `recommendedGrade === playerGrade` を高ウェイト（例: 4）、隣接学年を中ウェイト（例: 2）、その他を通常ウェイト（1）にする。
4. 算定された可変course・問題数を、course内の難度が急上昇しないように選ぶ。
5. seedをプロフィール・ステージ・挑戦回数から作り、コース開始時に問題IDと順番を保存する。

ウェイト値は実プレイデータで調整する。推奨学年が一致しない問題を排除してはいけない。

## 推奨データ形

物語基盤側の型変更と競合させないため、現時点では `questions.json` を編集しない。統合時は次のように、学年ではなく一本道の位置を正本にする。

```ts
type LinearQuestion = {
  id: string                 // 例: story-01-c01-q01
  storyStage: number         // 1..36
  course: 1 | 2 | 3 | 4 | 5
  order: 1 | 2 | 3
  recommendedGrade: 1 | 2 | 3 | 4 | 5 | 6
  sentence: string
  reading: string
  ruby: string[]
  romaji: string
  meaning: string
  sourceId?: string          // 再利用時の旧ID
  sourceEpisode?: string     // 例: 1-1。移動判断の監査用
  difficulty: {
    keystrokes: number
    words: number
    mora: number
    features: string[]
  }
}
```

`difficulty` は手入力せず生成時に算出する。最終JSONへ保存せず、検証時だけ導出する方式でもよい。問題本文の大規模生成は、物語基盤の `storyStage` とコース型が確定した後に行う。

## 実装ゲート

- 物語基盤の一本道IDが確定するまでは、`src/data/questions.json` を大規模編集しない。
- 最初にステージ1〜3の45問だけを作り、短さ・反復量・物語との自然さを実プレイ確認する。
- 承認後、ステージ4〜12、13〜24、25〜36の順で配信単位を分ける。
- 各単位で、問題数、ID一意性、ルビ整合、難度曲線、新要素の初出順をテストする。
